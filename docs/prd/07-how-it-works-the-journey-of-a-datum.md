# How it works: the journey of a datum

The simplest way to understand the platform is to follow a single datum from birth to an audit. The example uses requirement REQ-019 from the SKID-400 scenario: maximum operating pressure 17.2 bar.

1. **It is born in its tool.** REQ-019 is written in Polarion. The platform does not copy it: the adapter exposes it as a resource with an opaque, stable, resolvable URI registered by the Resolver.
2. **It is linked where people work.** An engineer, inside Capella, opens the delegated dialog and links LC-11 to REQ-019. The link is *asserted* in the system that owns the relationship and appears in the Link Index.
3. **It is checked.** Maturity shapes verify that the link is coherent: a released component cannot rest on a draft requirement. If it complies, the link becomes *validated*.
4. **It is projected.** The change event travels through the integration bus and updates the graph, which keeps provenance, version and configuration context. The pressure value is normalised by the Terminology Service next to the native one.
5. **It answers questions.** When someone asks what depends on REQ-019, the graph returns the complete impact in seconds and declares which nodes are not up to date.
6. **It changes under governance.** The customer asks for 21 bar: a Change is opened in the PLM backbone. The federated impact flags that PSV-418 is set at 18.5 bar before the change is made, and the owners receive work packages.
7. **It produces new results.** Calculation CAE-131 is rerun and published with a complete envelope; after review it is promoted to evidence in the PLM backbone.
8. **It is remembered.** Six months later an auditor asks for the state at the April baseline. The platform rebuilds it from events and preserved packages, and proves that no assertion in the evidence was generated by a model.

In none of these steps did the platform decide in a person's place: it connected, remembered and enforced approved rules.
